# Engines

`Frameworks/*.xcframework` are gitignored build products; when one is here, `Package.swift` uses it instead of the
release download. Rebuild with the scripts below; each script also writes a `Frameworks/<Name>.version` stamp with the
exact inputs used and a `Frameworks/<Name>.licenses.json` licence inventory of what it links (both gitignored, and
attached to each release).

Each has `ios-arm64`, `ios-arm64_x86_64-simulator`, `macos-arm64_x86_64`, `tvos-arm64` and
`tvos-arm64_x86_64-simulator` slices as static frameworks: the Go ones are cgo c-archives (gomobile
cannot target tvOS), HevSocks5Tunnel is C.

| `LibXray.xcframework` | `scripts/build-libxray.sh` (`LIBXRAY_REF`) | XTLS/libXray `v26.10.31` (7fe8528) → xray-core `v1.260327.1-0.20261031132019-a4a3dff5b20c` (Xray-core 26.10.31) without the YAML and TOML config loaders, with its timeout reader fixed, without its REALITY client's crawl, with a limit on the handshake response its WebSocket and HTTPUpgrade dialers read, and with limits on the response headers its XHTTP and gRPC dialers accept and the gRPC messages (`GoBridge/xray-core`) and REALITY `v0.0.0-20261014101318-83f621788ca8` without its fallback rate limiter (`GoBridge/reality`) | The latest libXray release when built; its `go.mod` asks for Go 1.27.3. Xray-core 26.6 and later refuse `allowInsecure` in a config, which the tunnel layer follows (it pins the peer certificate instead). The config loaders are left out because libXray passes JSON only, the rate limiter because its dependency, `juju/ratelimit`, is LGPL-3.0 and only a REALITY server uses it. Shadowsocks 2022 is no longer left out: since Xray-core 26.9.30 it is Xray-core's own code instead of the GPL `sing-shadowsocks`. `GoBridge/nogpl` checks every Go module's licence when an engine is built, and `scripts/check-frameworks.sh`, which `scripts/check.sh` runs, refuses a slice that links a GPL or LGPL module it names. The timeout reader fix: `TimeoutWrapperReader` returned no data and no error when its wait ran out, so the VMess outbound ended the request of an app that sends nothing for about 0.3 s plus the time to reach the node; it returns `buf.ErrReadTimeout` instead, as the pipe reader does; `scripts/check-frameworks.sh` checks that every slice has it. The REALITY client's crawl: when a server failed REALITY's verification, the client browsed the site that answered as a browser would, reading every page whole and keeping every link with no limit, and left the connection open, so a node with a real certificate for its server name could make the engine download without end; a client of one node has nothing to disguise, so it closes the connection (a censor that reroutes the connection to the real site sees a handshake closed with no request, where the crawl sent one), and `scripts/check-frameworks.sh` checks that no slice carries the crawl. The handshake response limit: Go's HTTP parser keeps a header line whole however long it is, and the HTTPUpgrade dialer read the response with no deadline, so a server that never ends its status line filled memory (WebSocket's 8 s handshake timeout bounded the time, not the bytes); both dialers now fail once the server has sent 64 KiB before the handshake ends, TLS included for WebSocket, and HTTPUpgrade's response must come within 8 s, unless it dials through another outbound (`dialerProxy`), whose connection ignores read deadlines, as WebSocket's 8 s timeout already did. The same patch keeps what an HTTPUpgrade server sends in the same packet as its 101 for the first reads: upstream copied it into a buffer as short as the first read, an empty one when the dial reads the response itself, which panicked and ended the extension; it also closes a connection whose handshake fails, which upstream left to the garbage collector, and gives the uTLS handshake of both dialers 8 s, which had no limit; `scripts/check-frameworks.sh` checks that every slice has the limit, the kept bytes and the TLS bound. The response limits: Go's HTTP clients accept 10 MB of response headers by default, grpc-go 16 MB and a 4 MiB message, which it lets a node send whole on each stream, one stream per connection in Tun mode; the XHTTP dialer accepts 64 KiB of response headers over HTTP/1.1 and HTTP/2, and the gRPC dialer 8 KiB (grpc-go's coming default) and messages of 32 KiB in Tun mode, the mode the tunnel layer dials, where an Xray-core server writes one buffer of 8 KiB, a V2Ray server one of 2 KiB, per message; grpc-go decodes a message into a pooled buffer of 32 KiB up to that size and of 1 MiB past it, which its pool keeps until a second garbage collection; TunMulti keeps the 4 MiB, as its messages carry as much as the server's buffer holds. A larger answer fails its request, and a gRPC header block far past the limit the connection to the node. HTTP/3, which only an `h3` ALPN picks, keeps quic-go's default. A server that pads XHTTP's response headers past 64 KiB (`xPaddingBytes`) is refused. `scripts/check-frameworks.sh` checks that every slice has the three limits. | 2026-11-13, go1.27.3 |

From 2.12.0 hev passes on the close of a TCP connection the proxy side ends; 2.8.0, carried over from the earlier Tun2SocksKit binaries, held it until `read-write-timeout` ran out.
